# 根因分析

## 推荐调用点与输入

Phase 1 / 6 / 7。Phase 2 需要补充故障依据时也可调用。
接收问题描述、预期与实际行为、复现步骤、本地源码和日志路径。
有 change 时先读其 proposal.md、bugfix-analysis.md、spec.md 中与问题相关的部分。

## 分析步骤

1. 固定一次失败的输入、环境、时间和可观察结果。不能复现时写明证据缺口。
2. 用 log-search 找现场证据，用 codegraph 或本地搜索追踪数据和调用链。
3. 对每一层因果问“为什么”。每个回答附文件位置或脱敏日志证据。
   5 Whys 是追因方法，不为凑满五层编造原因。未知处保留假设和验证办法。
4. 原因分叉时用鱼骨图思路分组：代码、数据、配置、依赖、环境、操作。
   区分触发条件、直接原因和根因。列出支持证据、反证及尚未排除的解释。
5. 给出最小修复建议、受影响路径、回归验证点。验证点说明修复前如何失败、修复后如何通过。

## 输出与边界

只分析不修改源码，不执行修复、配置变更或有副作用的复现。
只用本地材料，不连接外部服务。
输出按“现象 → 证据 → 因果链 → 根因或待验证假设 → 修复建议与回归点”组织。
证据写项目相对路径和行号。不得把相关性写成已证实的因果。

交回总控，由对应 Phase 的工件写作者按
[bugfix-analysis 模板](../spec-driven-dev/templates/bugfix-analysis.md)摘录到“现场证据”“根因分析”“修复方案”。
不创建额外 change 工件，不直接编辑 .meta.json 或 retrospective.md。
发现影响范围超出已有结论时，交回总控回退对应 Phase、修订工件并重过验证门。
本分析不能代替独立 QA 或评审结论。
