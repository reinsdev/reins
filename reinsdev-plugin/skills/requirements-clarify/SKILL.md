# 需求澄清

输入：用户需求、项目规约、当前 change 路径。只写本阶段 proposal.md。先读 [feature 模板](../spec-driven-dev/templates/proposal.md)，保留标题和表头；模板缺失就交回总控报告不可用。

## 对话与产出

1. 复述谁遇到什么问题、需要什么可观察结果。已有答案直接沿用，优先询问影响范围和正确性的未决项。
2. 从本地代码确认相关模块和约束，只读取证。把已知事实与待用户确认的业务决定分开。
3. 按模板逐节完成：

| 章节 | 写入内容 |
| --- | --- |
| 用户故事 | 每个核心功能一条，带故事编号、角色、能力和价值 |
| 验收标准 AC | 数字 AC 编号、关联故事、可测试的正常行为、具体验证步骤 |
| Out of Scope | 明确不做的事项；没有时显式写“无” |
| 歧义清单 | 问题、影响范围、类型、回答、来源、状态 |
| 隐含依赖 | 已有功能、外部系统及约束，无依赖时显式声明 |
| 5.1 字段映射确认表 | 源字段、目标字段、转换规则或固定值、来源 |
| 关键非功能性需求 | QPS、延迟、并发、数据量级与依据 |
| 影响的现有模块 | 模块、具体项目相对路径、影响说明 |

4. 业务取值的回答必须来自用户，来源填“用户”；映射实际确认后来源才填“用户确认”。命名等安全默认可注明真实来源，不能把 oemCode、格式、固定常量包装成安全默认。
5. 用户要求“先按合理默认继续”时，保留未答问题并说明需要哪项业务答案，不擅自标 ✅。无字段映射时写“本次无字段映射”并删除占位行。
6. 请用户核对范围、AC、字段映射。完成后移除已替换的占位说明；无歧义时明确写“无”。发现范围变化及时同步当前 proposal，交回后不修改已冻结工件。

交回总控，由总控跑 gate 1。返回 proposal 路径、未决问题和影响模块；正式选档及状态写入由总控通过 CLI 完成。
