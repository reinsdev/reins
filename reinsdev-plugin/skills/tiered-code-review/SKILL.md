# 分级代码评审规范

由独立 code-reviewer 执行。输入为项目规约、全部工件、基线与当前代码、static-analysis-report。只写自己的 code-review.md；不修代码、不改工件、测试预期或状态。

## 检查顺序

1. 先读 static-analysis-report，将机器已定位的问题作为已有证据。人工不重复登记同一问题；发现不同影响或遗漏证据时明确指出差异。
2. 按 baseCommit 到当前实现核对变更，逐项联系 AC、SC 和任务 scope。关注需求是否实现、业务映射是否遵从用户来源，以及是否越界修改。
3. 检查边界、异常处理、事务、幂等性、并发、权限、输入验证、资源释放与数据兼容；检查接口和数据库行为是否符合 spec。
4. 检查测试是否真正验证可观察行为，是否有空断言、只验非空、反射测私有方法等弱测试。核对测试实际运行和报告，不能用编译结果替代。
5. 检查层间依赖、命名语义、可读性、维护成本和必要的文档。建议必须对应具体证据，不能凭个人风格扩大 scope。

## 分级

| 级别 | 判定 | 后续 |
| --- | --- | --- |
| BLOCK | 会造成错误行为、安全问题、数据损坏、关键需求缺失或违反不可降级约束 | 阻止通过；修复或由用户本人按授权流程处理 |
| WARN | 需要处理的维护性、非阻断风险或技术债，有明确位置与影响 | 总控经 CLI 写入待优化清单；用户决定是否继续 |
| INFO | 不影响当前正确性的说明、观察或可选改进 | 记录即可，不伪装成必须返工 |

按实际影响分级，不能因测试绿灯降低已证实问题，也不能把单纯风格偏好升级成 BLOCK。无法验证的内容明确写出限制，不宣称已验证。

## 报告与交接

报告使用 [code-review 模板](../spec-driven-dev/templates/reports/code-review.md) 的共享骨架，T9 负责补充说明；模板缺失就报告能力不可用。首行必须为 `<!-- generated-by: code-reviewer-subagent -->`。保留“结论”的 `BLOCK | WARN | INFO` 表头，一行非负整数；“问题清单”的表头恰好是 `级别 | 位置 | 问题 | 建议`。位置写 `文件:行` 或 `-`。无问题时保留表头，不写数据行；计数须等于清单中对应级别的行数。

逐项给出具体问题、位置和修复建议。稳定编号、证据及影响可放补充说明，不增加或改写上述表头。

WARN 由总控使用 retro add 留痕，来源为 `code-review WARN`，内容必须与该行“问题”原文完全相等。评审者不得直接写 retrospective。BLOCK 返回对应 Phase 修正；报告结论不能替代用户放行或验收。修复后由独立评审者核验，不让主线把原条目改成已通过。

交回总控，由总控跑 gate 8。返回报告路径、BLOCK/WARN 数量、结论及未验证项；不要在主会话粘贴整份报告。
