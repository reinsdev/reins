# 事故分析

## 推荐调用点与输入

incident，可跨工件链调用。输入为用户提供的影响描述、事故时间、本地日志、配置快照和变更记录。
材料不足时列出缺失项。不要为补证据登录生产或查询外部平台。

## 分析步骤

1. 确认事故窗口、时区、受影响功能和用户范围。未知规模写“未知”。
2. 按时间排列发现、触发、扩散、缓解、恢复事件。每条附本地证据，标出时间误差。
3. 用 log-search 提取脱敏日志。需要追因时调用 root-cause-analysis。
   分开写已确认事实、假设和反证，不把“最近上线”直接认定为根因。
4. 说明故障传播路径、未及时发现的原因和现有防护缺口。
5. 给出止损建议、修复建议和长期预防建议。分别说明预期作用、风险、验证办法及回滚条件。
   负责人和完成时间未经用户确认时标为待确认。

## 输出与边界

只分析并给建议，绝不操作生产。不得执行远程部署、重启、回滚、数据修复或修改告警。
仅读取本地材料，不接外部服务。不修改源码和配置。
报告使用工作流规定的 `incidents/<date>-<topic>.md`，置于项目 `.openspec/` 下，
即 `.openspec/incidents/<date>-<topic>.md`，不放入 change 目录。
报告包含影响摘要、带证据的时间线、根因与置信依据、处置经过、改进建议及待确认事项。
已经存在的报告先读取，保留原有事实。引用路径用正斜杠，日志和身份信息先脱敏。

事故平息后的修复交回总控，由用户通过 /bugfix 或 /spec 进入工件链。
若已有 change 的结论被推翻，回退对应 Phase 并重过验证门。
不创建额外 change 工件，不直接编辑 .meta.json 或 retrospective.md，不代替用户做放行或验收决定。
