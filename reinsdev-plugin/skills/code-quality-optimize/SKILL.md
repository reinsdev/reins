# 代码质量优化

## 推荐调用点与输入

Phase 6 重构后 / Phase 8 前。先读当前任务 scope、关联 SC、变更文件和已有测试。
只分析不修改是未获实现授权或超出任务 scope 时的边界。
Phase 6 已授权任务范围内可直接重构。Phase 8 前发现需改代码的问题，交回总控路由到 Phase 6。

## 检查与实施

| 检查 | 判断依据 |
| --- | --- |
| 早期返回与嵌套 | 守卫条件能否减少嵌套，同时保留校验顺序和资源释放 |
| N+1 | 循环中的数据库或远程调用，结合本地查询日志、次数和数据规模确认 |
| 圈复杂度 | 分支数量、状态组合和已有测试是否足以支撑拆分 |
| 命名 | 是否表达业务含义，与 spec 中的概念一致 |
| 重复 | 是否确为同一业务规则，避免合并仅外观相似的逻辑 |

先给出文件位置、问题、影响和最小改法。没有测量证据时，性能收益标为待验证。
在授权 scope 内按 tdd-implement 规范做小步重构，保留可观察行为。
改变接口、业务取值、异常、事务边界或数据库语义时，停止重构并交回对应 Phase 更新规格。
修 bug 先补失败回归测试。重构运行已有相关测试，再按任务要求做构建与质量检查。
不得删除测试、弱化断言、改阈值或更新质量基线来制造通过。
无法本地验证时说明限制，不宣称优化成功。

## 输出与边界

只用本地代码、日志与工具，不接外部服务。
不越过任务 scope，不顺手处理其他模块的存量问题。
返回改动位置、行为保持依据、测试结果和未实施建议。
实施记录交给任务实现者，按 [implementation-log 模板](../spec-driven-dev/templates/implementation-log.md)填写。
评审时把分析证据交给独立 code-reviewer，由其决定 code-review.md 的级别；不自写评审结论。
不创建额外 change 工件，不直接编辑 .meta.json 或 retrospective.md。
交回总控，由总控跑受影响的 gate。延期问题由总控经 CLI 留痕。
