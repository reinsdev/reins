# 技术方案权衡

输入：冻结的 proposal、项目规约、现有系统；bugfix 加分析工件。只写 design.md，按 [design 模板](../spec-driven-dev/templates/design.md) 编写。需求错误先交总控回退，不在本阶段改 proposal。

1. 用需求目标解释成功标准，列出现有模块、具体文件路径、约束和改动影响面。
2. 提供至少两个可比较方案；L 档至少三个。每个方案包含核心思路、复杂度、优点、缺点、工作量、适用场景，不能只换方案名称。
3. 在“推荐方案与最终决策”中写出 `**AI 推荐**` 及具体理由；联系目标和约束，不写“视情况而定”。
4. 向用户呈报选择。尚未确认时，`**最终选择**` 保留待确认；不替用户落定。用户选择后将结果交总控执行 design set。
5. 总控确认 CLI 已记录用户决定后，将 `**最终选择**` 与理由回写为用户所选方案。改选 A → B 时保留原 AI 推荐，将最终选择明确改为 B；不能只在对话里确认。
6. 补齐“详细设计”的模块、数据流、接口签名和数据库概要；“风险与缓解”的风险、概率、影响、措施；“实施计划”的工期、依赖和上线风险。
7. “压力测试自检”逐条回答并发 10 倍、下游挂掉、3 个月后扩展、新人接手四个场景。回答要结合当前方案，不能只写“已考虑”。

交回总控，由总控跑 gate 2。返回 design 路径、用户选择与是否已同步、影响范围及未决风险；复杂度复评和升档决定由总控处理。
