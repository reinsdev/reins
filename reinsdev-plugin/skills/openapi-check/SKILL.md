# 接口契约比对

## 推荐调用点与输入

Phase 6 实现后 / Phase 8。总控在 `openapi.enabled=true` 时调用，也可按明确的契约核对请求调用。
输入为当前 spec.md、本机 Swagger/OpenAPI 端点或用户提供的本地导出文件，及可选 openapi.draft.json。
只分析不修改。缺少输入时明确未完成，不把“无法读取”当“一致”。

## 比对步骤

1. 读取 spec.md 的“接口契约”，保留关联 REQ/SC。不要自行补全未确认业务值。
2. 获取本地 code-first Swagger/OpenAPI，作为实现现状的权威来源。
   端点限本机回环地址。禁止访问远程服务器、跟随远程重定向或解析远程 `$ref`。
   本地文件导出注明来源、时间或版本；过期导出不能证明当前实现一致。
3. 检查输入格式及版本。按当前格式解析参数、请求体、响应与 schema；本地 `$ref` 只在给定材料范围内解析。
   引用缺失、循环无法处理、格式不支持或端点不可用时列出未比对部分，不安装工具或请求外部服务。
4. 按 HTTP 方法与路径匹配接口；比较参数位置、必填性、类型、格式、枚举、请求媒体类型、响应状态码、响应结构及认证要求。
   比较 schema 的 required/nullable、数组元素和嵌套字段，不因名称相同就判定兼容。
5. 与 spec.md 逐项列出“设计与实现漂移”。有草稿时另列草稿与实现的差异，不用草稿覆盖已确认 spec。
   删除接口或响应字段、增加必填输入、收窄输入取值、改变类型或认证要求等列为潜在破坏性变更，并说明受影响调用方。

## 输出与边界

输出数据来源和范围，再列方法/路径、spec 预期、实现实际、证据位置、兼容性影响和未验证项。
“权威实现”描述现状，不意味着可把 spec 静默改成实现。不能仅凭 OpenAPI 证明业务行为满足 SC。
不调用业务写接口，不启动服务，不改源码、spec、草稿或配置，不创建额外 change 工件。
差异交给独立 code-reviewer 摘录到 code-review.md，由其按评审规范定级。
需修改设计或实现时交回总控回退对应 Phase，重过验证门。
不直接编辑 .meta.json 或 retrospective.md，不代替用户放行或接受破坏性变更。
